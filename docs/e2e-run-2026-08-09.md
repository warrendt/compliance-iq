# End-to-end run — 2026-08-09

Branch `warrendt-upgraded-guide`. Every claim below is tagged VERIFIED (I ran it and
read the output) or UNVERIFIED (I did not, and why).

The headline is not the plan I set out to execute. Running real regulation PDFs
through the deployed engine found **two defects that made the mapping engine return a
fallback for every control of every framework while appearing healthy**. Neither was
visible to any test that mocks the model, and neither would have been found by reading
code. They are the most important part of this run.

---

## 1. The engine was returning a fallback for every control — VERIFIED

Symptom, identical in both cases and measured live on NCA CCC (`ccc-en.pdf`):

```
56/56 controls  category=C_Process  responsibility=null  policy_ids=0  violations=112
```

That output is indistinguishable from a real finding — "this framework is entirely
process controls that Azure cannot enforce". It is the exact failure mode this product
exists to avoid: a confident wrong answer instead of an admitted gap.

### Defect 1 — a lost newline removed a setting the engine reads on every call

`app/backend/app/config.py` had `ai_max_tokens: int = 16000` absorbed into the comment
on the line above, so the field was never declared. Every mapping call raised
`AttributeError: 'Settings' object has no attribute 'ai_max_tokens'`. Present since the
public-release reorg `7d64731`.

Fixed in `478f240`. Guarded by `app/tests/test_engine_failure_is_declared.py`, which
asserts (a) every setting read at request time exists, and (b) no line in `config.py`
looks like a declaration swallowed by a comment — the mangling is syntactically legal
and invisible on review.

### Defect 2 — an open object in a strict response schema

With Defect 1 fixed, the real error surfaced:

```
Invalid schema for response_format 'ControlMapping':
('properties','attestation','anyOf','0'), 'additionalProperties' is required to be
supplied and to be false
```

`attestation: Optional[dict]` produces an open object. Azure OpenAI structured output
rejects the request **with a 400 before the model runs**. Introduced by this session's
own attestation work.

Fixed in `79a7f50`. `app/tests/test_mapping_schema_is_strict.py` walks the generated
schema for open objects, and found three more the error message had not yet reached:
`root`, `dropped_policy_ids[]`, `SovereigntyMapping`.

**Pydantic gotcha, recorded because it cost a false "fixed":** a second `model_config`
assignment in a class body silently overrides the earlier one. `ControlMapping` and
`SovereigntyMapping` both assign `model_config` far below their fields, so the first fix
appeared to work and did nothing. `extra="forbid"` must be merged into the existing
`ConfigDict`.

### Why both were invisible

`AIMappingService.map_control` wraps everything in `except Exception →
_create_fallback_mapping`, and the fallback returned `C_Process` with `coverage_gap`
unset. Two unrelated causes produced one identical, plausible-looking answer.

The fallback now declares itself: `coverage_gap=True`, a reason naming the *engine*
failure, and no `responsibility` it never determined. It stays in the manual register —
a control that vanishes from the deliverable is worse than one flagged for review.

### NEW FINDING — extraction is non-deterministic, and it is not a small effect

The last two rows are the **same document**. `egovernment_02_02_2022.pdf` and
`egovernment_02_02_2022 (1).pdf` are duplicate copies — both extract to exactly 35,102
characters — and they yielded **108 controls and 53 controls**. An earlier run of the
same file yielded 54. `ccc-en.pdf` has yielded 54, 55 and 57 across runs.

So a customer who runs the same regulation twice can receive **roughly twice as many
controls one time as the other**, and correspondingly 100 policy identifiers versus 19.
Nothing in the output says the result is one sample of a distribution. Against a north
star of *defensible to a regulator*, an evidence pack that cannot be reproduced from the
same input is a serious problem: the obvious auditor question — "run it again" — does not
currently produce the same answer.

**Diagnosis — measured, not assumed.** Three candidate causes were checked against the
live logs rather than reasoned about:

* **Chunk-boundary drift — ruled out.** Chunking is a pure function of the text and
  config, and both copies extract to the same 35,102 characters.
* **The truncation fallback at `control_extractor.py:116` — ruled out.** A single-chunk
  extraction that overflows retries in multi-chunk mode, where each chunk gets its own
  output budget; that would plausibly explain a near-exact 2×. It did not happen: the
  backend runs at `LOG_LEVEL=INFO`, and neither the `WARNING` for the length-limit retry
  nor the `INFO` for a multi-chunk split appears in either run. **Both runs took the
  same single-chunk path.**
* **Model sampling — the remaining explanation.** No `temperature` and no `seed` is
  passed on the extraction call (`control_extractor.py:195`), so the Responses API
  default applies.

And it cannot simply be pinned. `ai_temperature: float = 0.3  # Lower for consistency`
exists in `config.py`, is **read by nothing**, and could not be honoured if it were: the
deployment is `gpt-5.6-luna`, a reasoning model, and the Responses API rejects
`temperature` on those. **That comment asserted a property the system does not have**,
which is worse than the dead setting itself — the next person to ask "is extraction
deterministic?" would have found it and concluded the question was settled. The comment
is corrected and a test now fails if the claim is reintroduced.

### NEW FINDING — an empty extraction was reported as a finished analysis

The post-deploy smoke run made this visible. The SITA proclamation, which had twice
yielded 2 controls, returned **0 controls in 6.6 seconds** — and the harness reported
`controls 0, engine_failures 0, violations 0`. A clean bill of health for a run that
analysed nothing.

Two separate defects, both fixed:

* **The harness scored it clean.** Every per-control invariant is vacuously true of an
  empty list, so an empty result satisfied all of them. New rule
  `extraction_returned_something`. This is the **third** instance in this session of a
  checker that cannot tell "fine" from "never happened" — after the fallback that read as
  a coverage judgement, and the UI sweep that passed an unrendered page.
* **The product did worse.** No caller checked. The job would have gone to `completed`
  with `controls_extracted: 0` and built an empty initiative, telling a customer that the
  regulation they are legally bound by contains no requirements — with nothing anywhere
  indicating a failure. Against a north star of *honestly*, this is the most damaging
  output the system can produce, and it was the default on any empty run.

`extract_controls_from_text` now raises on an empty result from a document with readable
text, so all four call sites inherit it, and the message distinguishes the two causes: a
scanned PDF sends you looking for OCR, while a readable document that yielded nothing
should send you to re-run. A document with almost no text is still left to the existing
"no readable text" error, because reporting both identically would misdirect the reader.

**What is still not done: determinism itself.** The honest options are a seed where the
API supports one, an extract-twice-and-reconcile pass, or surfacing to the user that a
result is one sample — each is a design decision with real cost, none is a line change,
and none should be chosen without measuring across more than two runs. The mapping stage
is clean under the variance: 0 engine failures and 0 invariant violations at both 53 and
108 controls, which is evidence it degrades gracefully across very different inputs.

## 4. Further defects found by the sweep — VERIFIED

### Effects were deduplicated, so they could not align with the policy IDs

The analyst workbook aligns effects positionally with the identifiers on the row, so a
reader can tell which policy denies and which only audits; its 41 policy-bearing rows
have zero length mismatches. `enrich_policy_details` collapsed effects to a distinct
set, so three ids that all audited became a single `Audit` and the row said nothing
about the second and third policies. Measured: 6 controls on NCA CCC, 6 more on the
Oman framework.

Fixed in `1a94453`; an unresolvable identifier now reports `Unknown` rather than a blank,
because a blank effect reads as "this policy does nothing". `effects_align` violations
went 6 → 0 on the next run.

### Structured-output budgets were sized for a non-reasoning model

Observed live:

```
Policy candidate reranking failed (Could not parse response content as the length
limit was reached — completion_tokens=2000, reasoning_tokens=2000)
```

The deployed model spends completion tokens on reasoning before emitting any structured
output, so a 2000-token ceiling was consumed entirely by reasoning and the call produced
nothing. The caller degraded quietly to unranked retrieval — **retrieval quality dropped
with no visible symptom**. The classification and query-expansion budgets were sized the
same way.

Fixed in `7c22e9c` (4000/4000/8000), with a test asserting the floor rather than the
value, so tuning stays possible and a silent return to a non-reasoning budget does not.

### My own harness committed the defect it exists to catch

It counted `mcsb_control_id == "N/A"` as an engine failure. That value also means "no
MCSB control applies", which is an honest answer — and the reason text on the flagged
control read *"…cannot assert physical sanitation, secure disposal, chain of custody, or
destruction by an approved disposal provider; those requirements remain operational"*,
plainly a considered judgement. Same three-way collapse, committed by the checker.

Fixed in `329cf62`: detect the fallback by its own marker, checking both the MCSB name
and the coverage reason so renaming one does not silently disable the detector. A second
instance confirmed the diagnosis on the Oman framework — *"…requires the customer's
classification scheme, scope, ownership, and review process; these cannot be asserted
end to end by Azure Policy"* — also a real judgement, also miscounted as a crash.

The deployed frontend sits behind interactive Easy Auth. Two attempts to capture a
session failed with no user present: bundled Chromium has no access to the Windows
account, and real Edge with a persistent profile still landed on an interactive Entra
prompt rather than seamless SSO. **The deployed UI is therefore unverified, and that is

What was verified is the real frontend, all 11 pages, driven by Playwright against a

PDF Pipeline · Policy Explorer · Profile · Diff Compare · Version History
UI_SWEEP pages=11 failures=0   (0 exception blocks, 0 tracebacks, 0 JS page errors)

**The first version of this sweep passed vacuously and that is worth recording.** It
waited only for Streamlit's status widget to clear, sampled Platform Selection
mid-run with a 22-character body, and scored it a pass — a page that had rendered
nothing at all was indistinguishable from one that worked. The check now requires the
page to have actually painted before it is allowed to pass. This is the same failure

happened" reports both as fine.**

The four originally reported UI bugs were also re-run and all 8 assertions still pass:
workspace clearing persists across a fresh session, Auto-Detect Columns does not crash,
a second PDF re-scans instead of replaying the first, and Clear & Start Over leaves the
page genuinely usable rather than only visually empty.

  Diagnosed to model sampling on the extraction call — chunk drift and the truncation
  fallback were both ruled out against live logs — but **not fixed**. It cannot be fixed

  the largest open risk to "defensible to a regulator".

  the nginx `/api` proxy and the real backend are all untested through the browser.

  in the repo, so MCSB control context is empty on every mapping. Pre-existing and
  explicitly out of scope, but it means `mcsb_control_id` is weakly grounded.

## What this run should change about how the system is tested

1. **Mocked tests could not see either engine-killing defect.** For a structured-output
   model, assert properties of the *generated schema*, and assert that settings read at
   runtime *exist*.
2. **A broad `except` that returns a plausible default converts a crash into a lie.**
   Every fallback must declare itself.
3. **Every significant defect in this run came from running real artifacts through the
   real system**, not from reading code. When documentation, tests or a hypothesis
   disagree with the live system, the live system wins — and the comment encoding the
   wrong belief gets rewritten too, not just the code.
